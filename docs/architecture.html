🌳 Grove Platform — Architecture

A multi-tenant commerce + settlement + fulfillment platform: one codebase, one deployment, one Payload instance. Each customer organization (tenant) is resolved at runtime from the hostname — no forks. This page covers what the pieces are, how tenancy works, and how an order & its money flow through the system.

App (a running website) Package (shared code) Engine / service (deterministic logic) External service / provider

1 System components

Everything lives in one Turborepo + pnpm monorepo. Three apps are visited in a browser. Engines are deterministic services (no AI) that do routing, inventory, ledger, and payout work. Packages are shared building blocks. External providers are reached through swappable adapters.

3 How multi-tenancy works

There are no per-customer copies. The hostname decides which tenant's data is shown, and @payloadcms/plugin-multi-tenant automatically scopes every query to that tenant. Collections are either global (shared across all tenants) or tenant-scoped.

request
Visitor opens a URL
e.g. acme.grove.app
middleware
Read the hostname
Next.js middleware inspects the domain.

Match to a tenant
Hostname → the right Org (tenant) record.

Auto-filter queries
Plugin limits all data to that tenant.

Only their data appears.
Global collections not scoped

Shared across the whole platform. Identity and the tenant registry live here.
Tenant-scoped collections auto-filtered
sitesproductsorderspaymentspartnersinventory-levelsfulfillmentsledger-*settlementspayout-*compliance-checksaudit-logs…
Every new collection is tenant-scoped unless genuinely global. Registered in two places: the collections array and the multiTenantPlugin map.

Access control is centralized in packages/payload/src/access.ts — isAuthenticated, isSuperAdmin. Partner users (partner_admin / partner_operator) are further scoped to their own partner. Money is always stored as integer minor units (cents) + currency to avoid float drift.

4 Request & money data flow

From an order on the storefront to money paid out to partners. The API layer is server-authoritative: it recomputes totals from DB prices (never trusts the client) and uses idempotency keys. The deterministic engines do the rest. See Settlement Flow for the annotated sequence.

1 · order
Place order
apps/web checkout calls the create-order route.
2 · pay
Authorize payment
PaymentProvider adapter authorizes the amount.
3 · route
Routing Engine
Picks a partner location with stock in range.
4 · fulfill
Fulfillment
Partner accepts → in transit → delivered.
5 · ledger
Ledger postings
Double-entry, immutable, balanced.
6 · settle
Settlement split
Platform fee / supplier / partner per tenant config.
7 · payout
Payout batch
Payout Engine aggregates payable balances.
8 · disburse
Provider pays
PayoutProvider sends ACH/RTP; status tracked.

Cross-cutting the whole flow: Compliance can gate checkout on a passing eligibility check (config-driven per tenant), and audit-logs append-only records every key action (order placed, status change, payout, refund). Routing, settlement math, and payout aggregation are deterministic code — AI stays in the existing Service/AI layer.
